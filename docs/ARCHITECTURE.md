# Архитектура Wrocław Analyzer

Отдельная система по образцу киевского RE Analyzer: своя папка, своя база,
свой сервер и своё расписание. Общего кода с киевской системой **нет** —
скопированы только решения, которые там окупились (см. RESEARCH.md, §6).
Стек тот же, чтобы владельцу не учить второй: **FastAPI + SQLite + React/Vite**,
Python ≥ 3.9 (синтаксис 3.9), Node 18+.

## 1. Контуры

```
            ┌──────────── прогон (scraper.py) ────────────┐
 otodom ──▶ │ адаптер │ нормализация │ upsert + история │ ──▶ listings
 olx    ──▶ │ sources/ │ normalize.py │ цен, снятие      │      price_history
            └──────────────────────────────────────────────┘      scrape_runs
                              │ после прогона
                              ▼
      dedup.py ──▶ analytics.py ──▶ rent_analytics.py ──▶ translate.py ──▶ fx.py
      (дубли)      (выгодность,       (доходность)          (PL→UK,         (НБП)
                    индекс, срезы)                            очередь, кэш)
                              │
                              ▼
                     main.py (FastAPI, basic-auth) ──▶ frontend/dist (React)
```

Два вида объявлений живут в ОДНОЙ таблице `listings` и различаются полем
`offer_type` (`sale` | `rent`): у них одинаковые поля, одинаковые источники и
одинаковая обработка, а доходность считается соединением одного с другим.
В Киеве аренда была отдельной таблицей, потому что у неё был другой источник
и другие поля; здесь причины дублировать код нет.

## 2. Хранилище (`backend/app/models.py`)

`listings` — одно размещение на одной площадке. Ключ уникальности
`(source, source_id)`. Группы полей:

- **источник**: `source`, `source_id`, `url`, `external_url` (OLX → otodom),
  `raw_json` (сырой ответ, для повторного разбора без скрапа);
- **текст**: `title_pl`, `description_pl`, `title_uk`, `description_uk`,
  `translated_at`, `translate_provider`, `translate_version`;
- **цена**: `price_pln`, `price_per_m2`, `czynsz_pln` (эксплуатационный
  платёж, у аренды — «dodatkowo»), `price_usd`, `price_eur` (по курсу НБП на
  день `last_seen`, для привычки владельца думать в долларах);
- **квартира**: `area`, `rooms`, `floor` (0 = parter), `floors_total`,
  `build_year`, `market` (`primary` | `secondary`), `building_type`,
  `building_material`, `construction_status`, `condition` (см. §5),
  `condition_override`, `ownership`, `heating`, `windows`, `elevator`,
  `furnished`, `extras_json`, `media_json`;
- **место**: `district` (5 дзельниц), `osiedle` (48), `osiedle_override`,
  `osiedle_src` (`geo` — осиедле не от площадки, а по координатам, см. §4а),
  `street`, `lat`, `lon`, `address_raw`;
- **продавец**: `seller_type` (`private` | `agency` | `developer`),
  `seller_name`, `no_commission`;
- **жизнь**: `posted_at` (по данным площадки), `first_seen`, `last_seen`,
  `is_active`, `removed_at`, `image_count`, `images_json`;
- **дубли**: `dedup_group`, `group_size`, `is_representative`;
- **выгодность**: `discount_pct`, `baseline_sqm`, `baseline_level`,
  `baseline_count`, `deal_thin_base`, `deal_updated_at`;
- **доходность**: `rent_median_pln`, `rent_baseline_level`,
  `rent_baseline_count`, `yield_pct`;
- **владелец**: `is_favorite` (общий флаг, остался с однопользовательской
  поры), `note`.

`price_history(listing_id, price_pln, seen_at)` — только при СМЕНЕ цены
(как в Киеве: цена на дату — переносом последней известной).

`scrape_runs` — прогон: `kind`, `source`, `status` (`running` | `done` |
`failed` | `stopped`), счётчики, `last_beat`, `last_page` (для
возобновления), `log`.

`translations(hash, dst_lang, provider, model, text)` — кэш переводов;
`fx_rates(date, code, mid)` — курсы; `settings(key, value)`;
`user_actions` — журнал ручных правок (что и когда владелец поменял).

Появились вместе с отдельными логинами:

- `favorites(user, listing_id, created_at)` — обране У КАЖДОГО СВОЁ.
  Общий `listings.is_favorite` остался для совместимости, но правда здесь:
  если Юлия отметила квартиру, владелец этого в своём списке не видит.
- `user_profiles(user, display_name, phone, email, agency, about, pres_lang,
  updated_at)` — визитка риелтора для PDF-подборки. Чужую не отдаём
  никому, включая владельца.
- `access_log(user, at, method, path, query, status, ip)` — раздел «Журнал»:
  кто что смотрел и менял.
- `unknown_values(field, value_pl, count, last_seen)` — структурные значения,
  которых нет в словаре `i18n.py`; копятся и видны в «Прогонах».

Схема мигрируется сама при старте (`db.ensure_columns`: недостающие
колонки И индексы), новые таблицы создаются там же.

**Сколько стоит прочитать строку.** `raw_json` и `description_pl` лежат в той же
таблице, поэтому средняя строка весит **~32 КБ** — восемь страниц. Любой
поиск по обычному индексу дочитывает строку целиком, и срез по 12 тыс. объявлений
ради трёх чисел превращается в ~400 МБ чтения. Поэтому у всего, что считается
регулярно, должен быть **покрывающий** индекс (все нужные колонки внутри), иначе
таблица читается целиком. Проверка: `EXPLAIN QUERY PLAN` должен сказать
`USING COVERING INDEX`; `USING INDEX` без `COVERING` — значит, строки дочитываются.

## 3. Прогон (`scraper.py`)

Фазы одного прогона по одному источнику:

1. **Обход выдачи** — страницы по порядку, темп ≤ 15 запросов/мин
   (`fetcher.Throttle`), случайная пауза. Каждое объявление → `normalize` →
   upsert. У новых `first_seen = now`, у всех увиденных `last_seen = now`;
   смена цены пишет `price_history`. Страница фиксируется в `last_page`
   после коммита — упавший прогон продолжается с неё.
2. **Хвост** — только Otodom: у новых объявлений качается карточка ради
   описания, характеристик и координат (на выдаче их нет). OLX отдаёт всё
   сразу — хвоста нет.
3. **Снятие** — после ПОЛНОГО успешного обхода источника объявления этого
   источника, не виденные `INACTIVE_AFTER_DAYS` (3) дня, получают
   `is_active = 0`, `removed_at`. Строки не удаляются никогда (политика
   владельца из Киева: снятое объявление — наблюдение о рынке).
4. **Пересчёт** — дубли → курсы → выгодность → доходность. Каждый шаг ловит
   своё исключение и пишет в лог, не роняя прогон.
5. **Перевод** — НЕ шаг прогона: очередь стартует отдельным потоком, когда
   прогон уже закрыт (`scraper.translate_after_run`). На общей с другой
   системой видеокарте перевод — это часы (замер 18.09.2026: 36 с на запрос),
   и как шаг прогона он держал бы «прогон идёт» — триггеры получали бы 409.

Правила, перенесённые из Киева как есть:

- **отметка жизни** (`last_beat`) пишется отдельной сессией
  (`beat_apart`), чтобы не делать `commit` на сессии с открытым курсором;
- **ошибка записи → `db.rollback()`**, иначе сессия отравлена до конца прогона;
- **источники по очереди**, никогда параллельно (один домашний IP);
- **пауза** (`scrape_paused_until` в настройках) сворачивает текущий прогон
  за полминуты и не даёт стартовать плановым; статус такого прогона —
  `stopped`; в шапке интерфейса — красная плашка;
- **сторож**: прогон без отметки жизни 3 часа закрывается как `failed`.

Полный обход: Otodom ≈ 150 страниц по 72 (10–15 мин при 15/мин), OLX ≈
250 страниц по 40 (~20 мин, с дроблением по цене из-за потолка offset).
Хвост Otodom — по числу новых, ~300–500 карточек в день ≈ 25–35 мин.
Итого прогон продажи ≈ 1 час, аренды ≈ 30 мин.

## 4. Дубли (`dedup.py`)

Одна квартира стоит на Otodom и OLX (зеркало), у двух агентств, и у агентства
и собственника. Ключи склейки, по убыванию силы:

1. `external_url` OLX → id Otodom (точное зеркало);
2. `(rooms, round(area), floor, osiedle|district, price ± 3%)` — та же
   квартира по числам;
3. совпадение первой фотографии по URL на CDN (у зеркал одна и та же
   картинка `ireland.apollo.olxcdn.com`).

Перцептивный хэш фото — DEFERRED (фото не скачиваем). Представитель группы
(`is_representative`) — самое дешёвое активное размещение; в каталоге по
умолчанию показываются только представители, остальные — в карточке. Кнопка
«інша квартира» (detach) есть с первого дня: киевский опыт говорит, что
барьера, который не ошибается, не существует.

## 4а. Осиедле по координатам (`geo_knn.py`)

OLX даёт только дзельницу (5 на город), а осиедле из одной дзельницы
не выводится. Без осиедле объявление сравнивается с чужими квартирами
(пул сразу падает до уровня дзельницы, §6) и не склеивается «по числам»
(§4, ключ 2). Но координаты дают оба источника.

Решение — ближайшие соседи по тем объявлениям, где осиедле назвала сама
площадка (Otodom, ~10 800 точек). K = 9, ответ засчитывается только при
согласии ≥ 6 из 9 в радиусе 900 м — иначе «не уверен» и поле остаётся
пустым: лучше молчать, чем назвать чужой район и испортить медиану.
Проставленное помечено `osiedle_src='geo'`; в таблице рядом с таким местом
стоит «≈». Карта строится ТОЛЬКО из строк с `osiedle_src IS NULL`, иначе
собственные догадки стали бы источником истины для следующих.

Проверено перекрёстно (`scripts/fill_osiedle.py --check`, 1500 скрытых точек):
ответ дан в 98,7% случаев, верен в 98,5%; все ошибки — соседние осиедле
на границе. Шаг встроен первым в `post_process` прогона: и склейка, и пулы
выгодности опираются на место. На боевой базе 24.09.2026: без осиедле было
5710 активных, стало 367 (продажа 83,3% → 99,4%, аренда 46,2% → 95,6%).

## 5. Класс состояния (`normalize.condition`)

Польский аналог киевского «ремонта» — три уровня и «неизвестно»:

| Класс | Признаки (характеристики + слова) |
|---|---|
| `developer_bare` | `construction_status=to_completion`, «stan deweloperski», «do wykończenia» (рынок в классификации не участвует) |
| `to_renovate` | «do remontu», «do generalnego remontu», «do kapitalnego remontu» |
| `to_refresh` | «do odświeżenia», «do odnowienia», «wymaga odświeżenia» |
| `renovated` | «po remoncie», «po generalnym remoncie», «wykończone», «gotowe do zamieszkania», «wysoki standard», «pod klucz», `construction_status=ready_to_use` + первичка с отделкой |
| `unknown` | ничего из этого |

Класс — корзина сравнения в оценке выгодности; ручная правка
(`condition_override`) сильнее автомата и скрапом не перетирается. Порядок
(`classify_condition`): слова «do remontu» → статус `to_renovation` → слова
застройщика → статус `to_completion` → «odświeżenia» → «po remoncie» → статус
`ready_to_use`; иначе «po remoncie kuchni, reszta do remontu» ушло бы в
«renovated». Слово с отрицанием перед ним («nie wymaga remontu», «żadnego
remontu» — до трёх слов, не через знак препинания) признаком не считается
(15.10.2026; «bez» не отрицание: «bez windy, po remoncie»).

## 6. Выгодность (`analytics.py`)

Тот же принцип, что в Киеве: цена за м² объявления против **медианы пула
похожих**, пулы ищутся от узкого к широкому, пока не наберётся минимум:

| Уровень | Ключ пула | Минимум |
|---|---|---|
| `osiedle_rooms` | осиедле × комнаты (4 = «4+») | 6 |
| `osiedle` | осиедле | 8 |
| `district_rooms` | дзельница × комнаты | 10 |
| `district` | дзельница | 12 |
| `city_rooms` | город × комнаты | 15 |
| `city` | город | 20 |

К месту в ключе добавлены **рынок** (свой / `any`), **класс состояния** (свой /
`mixed`) и **эпоха дома** (своя / `any`). В пулы идут только активные
представители групп склейки; из базы квартиры исключены она сама и её дубли
(вся группа). Порядок перебора:

1. уровни места от узкого к широкому; на каждом — варианты (рынок, класс):
   свой+свой → свой+смешанный → любой+свой → любой+смешанный (у `unknown` —
   только смешанный класс);
2. внутри варианта — сначала дома той же эпохи, если их **не меньше 10**, иначе
   все эпохи (с поправкой на возраст, см. ниже);
3. у классов `to_renovate` и `developer_bare` — сначала свой класс на ВСЕХ
   уровнях места и только потом смешанный: иначе цена ниже рынка ровно на
   стоимость ремонта выдавалась за скидку (15.10.2026: из 208 «выгодных» под
   ремонт 162 получили скидку так);
4. «do wykończenia» на вторичке в доме, который не новостройка (до 2015 г.;
   год неизвестен — по типу дома), сравнивается как `to_renovate`: это квартира
   под полный ремонт, а пул `developer_bare` на 94% из новостроек
   (`analytics._bucket`). Показанное состояние не меняется.

Цена за м² приводится к общему знаменателю двумя поправками, обе **меряются на
своих данных при каждом пересчёте** и пишутся в настройки (`area_coef_sale`,
`era_coef_sale`):

* **площадь** — медиана zł/м² по полосам площади относительно 45–60 м²
  (ограничена 0,7–1,3; в Киеве метр дешевеет на 3–6% за полосу, здесь своё);
* **возраст дома** — эпохи до 1945 / 1945–1999 / 2000–2014 / 2015+; внутри
  осиедле на вторичке «з ремонтом» медиана эпохи против медианы осиедле,
  медиана таких отношений по осиедле (15.10.2026: 0,889 / 0,938 / 0,996 /
  1,125). Без неё скидка измеряла возраст: «выгодными» были 38% квартир в
  домах до 1945 г. и 4% в новостройках.

Скидка = 1 − price_sqm_adj / медиана. При `n < 10` в найденном пуле —
`deal_thin_base = 1`: карточка и список пишут «база тонка», а пресеты
«Вигідні» и счётчик на главной такие не берут (`thin_base=exclude`).
Санитарные пороги (4 000–40 000 zł/м², от 12 м²) отсекают мусор до расчёта.
Карточка показывает уровень, ключ пула словами, медиану, обе поправки;
`scripts/explain_deal.py` — перебор шагов тем же кодом.

Известные пределы метода (для аудита): нет «класса проекта» — в маленьком
элитном осиедле пул первички состоит из одного-двух дорогих проектов; площадь
чердаков и антресолей, «две квартиры по цене одной», cesja и т. п. не
распознаются и выходят в верх списка выгодных; полоса «100+ м²» одна на все
большие квартиры.

**Индекс цен** — по ОДНИМ И ТЕМ ЖЕ объявлениям (месяц к месяцу медиана
изменения цены у объявлений, живших на обеих границах), а не медиана по дате
подачи (выживаемость: дешёвое уходит быстрее). `price_history` пишется только
при смене цены → цена на дату переносом последней известной.

## 7. Доходность (`rent_analytics.py`)

Медиана ставки zł/м² по уровням (осиедле × комнаты → осиедле → дзельница ×
комнаты → дзельница → город × комнаты → город; минимумы 5/8/8/12/15/20) из
активных представителей `offer_type=rent` с правдоподобной ставкой (20–250
zł/м²) и **без комнат на съём** (`is_room_rental`: единственное число «pokój»
без признаков целой квартиры; 30 из 4124 на 15.10.2026). Ставки приводятся к
средней площади и к типичному для осиедле возрасту дома — поправки свои,
измеренные на аренде (`area_coef_rent`, `era_coef_rent`; 15.10.2026: дом 2015+
— 1,075, 1945–1999 — 0,914). Ожидаемая ставка = медиана × площадь × поправка
площади × поправка эпохи этой квартиры; валовая доходность = ставка × 12 /
вложения. Квартира продажи — с тем же санитарным фильтром, что и у
выгодности. У `developer_bare` и `to_renovate` в знаменателе цена **плюс
отделка** (`renovation_cost_sqm_pln`; решение владельца 24.09.2026 — $1000/м²
= 3 860 zł/м²). Czynsz administracyjny не вычитаем: на аренде его обычно
платит арендатор сверх ставки. «Найкраща дохідність» (`yield_top`) — ставка
места против цены места, обе без поправки на возраст. Подсказка в карточке
пишет, из какого уровня взята ставка и сколько объявлений в базе.

## 8. Перевод (`translate.py`, `i18n.py`)

- `translate_provider`: `ollama` (по умолчанию) | `anthropic` | `google` |
  `deepl` | `none`. Каждый провайдер — функция `translate(texts) -> texts`,
  общий интерфейс, общий кэш по SHA-1 текста.
- Очередь: новые активные объявления без `title_uk` → заголовки (короткие,
  все сразу); без `description_uk` → описания, не больше
  `translate_daily_cap` в сутки (по умолчанию 800), самые новые первыми —
  по дате подачи (`posted_at`), а не по `first_seen`.
  Ручка `POST /api/listings/{id}/translate` переводит одну карточку вне очереди
  (и обновляет перевод прежней версии подсказки).
- Ollama: `translate_ollama_num_ctx` должен совпадать с CONTEXT уже
  загруженного экземпляра той же модели (`ollama ps`), если карту делит другая
  система, — иначе модель перезагружается на каждый запрос (15–25 с против 0).
- Структурные поля (тип дома, рынок, отопление, окна, собственность,
  состояние, дополнения) → словарь `i18n.py`; осиедле и дзельницы →
  транскрипция в `geo.py`. Значения, которых нет в словаре, показываются
  по-польски с пометкой — и попадают в отчёт «незнакомые значения», чтобы
  словарь пополнялся.
- Оригинал хранится всегда и показывается рядом с переводом; перевод можно
  пересчитать другим провайдером (`translate_version`).
- Подсказка модели фиксирует термины: «stan deweloperski» → «стан від
  забудовника (без оздоблення)», «czynsz» → «експлуатаційний платіж»,
  «rynek wtórny/pierwotny» → «вторинний/первинний ринок», «kamienica» →
  «кам'яниця (старий будинок)», «blok» → «панельний/блочний будинок».
  Версия подсказки — `PROMPT_VERSION`; меняли — поднять: кэш действует в
  пределах версии, старые переводы станут «устаревшими» в отчёте и
  обновляются кнопкой карточки.

## 9. Валюта (`fx.py`)

Цены в PLN. Раз в сутки — `api.nbp.pl` таблица A: USD и EUR (`mid`), кэш в
`fx_rates`. `price_usd`/`price_eur` пересчитываются у активных объявлений
при каждом прогоне, чтобы сортировка по долларам не требовала джойна.

## 11. Расписание, деплой, сосуществование с киевской системой

Хост — **ПК с Windows 11** (решение владельца 18.09.2026: больше места на
диске, там же Ollama с видеокартой). Код — в git, база — локальный файл
SQLite на этом ПК (`WRO_DATA`, большой диск), с Mac ничего переносить не надо.

- Порты: боевой сервер **8020**, превью на копии базы 8000, dev-сервер Vite
  5175. Все три записаны в общем справочнике портов (`/api/net` реестра,
  CLAUDE.md «Общие ресурсы ПК»); новый порт — только через `/api/net/free`.
  Превью было на 8021, переехало 27.09.2026: Windows держит 8021–8220
  (`netsh interface ipv4 show excludedportrange protocol=tcp`), и занять их нельзя. Переменные: `WRO_DB`, `WRO_DATA`, `WRO_WEB_PASS`, `WRO_PORT`,
  `DISABLE_SCHEDULER`. Всё — в `deploy/windows/env.ps1` (не в git), его
  читают и сервер, и триггеры, и `safe_restart` — пароль в одном месте.
- Расписанием управляет **Планировщик заданий Windows**
  (`deploy/windows/install.ps1` регистрирует `WroAnalyzer-Server`,
  `WroAnalyzer-Scrape-Sale-11/-17`, `WroAnalyzer-Scrape-Rent` 02:30).
  У сервера ДВА триггера — при запуске Windows и при входе в систему:
  до 09.10.2026 был только второй, и после перезагрузки на обновления сайт
  не поднимался, пока владелец не сядет за компьютер. У всех задач —
  вход **S4U** (работают без входа в систему, пароль нигде не хранится),
  `-StartWhenAvailable` (пропущенный прогон выполняется при первой
  возможности, а не теряется до завтра) и перезапуск при сбое.
  `install.ps1 -TasksOnly` переставляет только расписание, не трогая
  зависимости; без прав администратора отказывается сразу, не гася сервер.
- Внутренний APScheduler прогонов — только для разработки
  (`DISABLE_SCHEDULER=1` в бою, иначе двойной запуск). Рядом работает второй,
  **сторожевой**, включённый ВСЕГДА — в нём пять заданий (видны в `/api/jobs`):
  `watchdog` (10 мин, закрывает зависшие прогоны), `summary-warm` (2 мин, греет
  кэш сводки), `wal` (15 мин, подрезает журнал SQLite),
  `translate-retry` (час, добивает очередь перевода, когда свободна карта),
  `backup` (04:30, снимок базы).
- `server.ps1` держит uvicorn в цикле (аналог KeepAlive), пишет PID в
  `server.pid`. **С 10.10.2026 перезапуск требует прав администратора**: задачи
  созданы с входом S4U, и из обычного PowerShell их не остановить. Без прав
  `safe_restart.ps1` говорит об этом и печатает готовую команду с запросом
  прав — важно помнить при каждой выкатке. Сам скрипт отказывается
  перезапускать во время прогона
  (`-Wait` ждёт окна); `scrape_trigger.ps1` — POST `/api/scrape` с паролем и
  случайной задержкой 0–20 мин, аренда повторяет при 409 каждые 15 мин.
- **Окна прогонов не пересекаются с киевскими** (те идут 8/14/20 Киев +
  30–50 мин и хвост до часа; аренда 13:05–13:25), потому что IP тот же
  домашний: продажа в **11:00 и 17:00**, аренда в **02:30** по Киеву.
- Логи: `%WRO_DATA%\server.log` — ротацию делает сам Python
  (`RotatingFileHandler`, 20 МБ × 3), `trigger.log` обрезает триггер.
- **Копии базы**: `%WRO_DATA%ackup\wro-ГГГГ-ММ-ДД.db`, ежедневно в 04:30,
  храним три последние. `VACUUM INTO` — цельный снимок без WAL прямо на
  работающей базе (958 МБ за 3 с). Скрап повторим, а история цен, ручные
  правки, обране и журнал — нет.
- Доступ с Mac и телефона в той же сети: **`http://192.168.50.20:8020`**
  (адрес ПК закреплён на роутере; справочник — `/api/net` реестра).
  Сервер слушает `0.0.0.0`, правило брандмауэра (профиль «Частная сеть»)
  ставит `install.ps1`. Вход по паролю нужен и в домашней сети. Доступ снаружи (DuckDNS/TLS, как в Киеве)
  — когда понадобится Юлии; пока не делаем.

## 12. Проверка правок

Копия базы (`sqlite3.backup()` → `data/wro-copy.db`), `WRO_DB=<копия>` в
`.claude/launch.json` → превью на 8000, dev-сервер фронта на 5175 с
`VITE_API=http://127.0.0.1:8000`. Три уровня проверки, каждый ловит своё:

1. `pytest tests -q` — парсеры на фикстурах, нормализация, дубли, выгодность,
   доходность, очередь к видеокарте, API на пустой базе.
2. `scripts/ui_check.py` — фронтенд на фикстурах: все разделы, обе роли,
   тёмная тема, снимки экрана. Поломки вёрстки и пустые состояния.
3. `scripts/live_check.py` — **БОЕВОЙ** сайт браузером: 11 разделов и карточка
   на настоящих данных, ошибки в консоли, снимки. Пароль берёт из
   окружения (`. .\deploy\windows\env.ps1` перед запуском). Фикстуры не покажут
   того, что пришло из базы: 09.10.2026 именно так нашлись прочерки на
   главном экране и фальшивый список «Знизили ціну».
Первый запуск на новом месте — `scripts/probe_sources.py` (см. RESEARCH §0).
